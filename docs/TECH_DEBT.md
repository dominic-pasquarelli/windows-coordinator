# Tech Debt Register — Windows Coordinator

> The single canonical home for **known limitations, accepted couplings, and deferred cleanups** —
> the things this project chose to live with, on purpose, with a paper trail.
>
> **One sentence:** everything here is a thing we know is wrong and decided not to fix yet, together
> with the condition that should change our mind.
>
> **Relationship to the audit.** The [audit protocol](AUDIT.md) is how debt gets *found*; this
> register is where a known-and-accepted item *lands* so future audits do not re-litigate it. When an
> audit produces a "known limitation" finding, it becomes a row here. When an item is paid down, it
> moves to **Paid** with the change that did it — the ledger is the point, because a register that
> only ever grows tells you nothing about whether the project is getting healthier.

---

## How this register works

- **Every item has a stable ID** (`TD-N`) so code comments, ADRs, [NEXT.md](NEXT.md) and audit
  entries can reference it by name. **Never reuse an ID.** A paid item keeps its number and moves to
  the Paid section — the number is a permanent handle on a specific piece of history.
- **Cost / risk** is a rough triage signal, not a promise:
  🔴 *active* (paying interest right now — fix when the triggering work lands) ·
  🟡 *latent* (fine today, will bite at a known future point) ·
  ⚪ *cosmetic* (no functional cost; consistency or legibility only).
- **Every row names a TRIGGER** — the specific condition that turns a latent item active. This is
  what keeps the register from being a list nobody reads: each item knows when it becomes due, so it
  can resurface on its own rather than depending on someone remembering it. A trigger that reads
  "eventually" is not a trigger.
- **Adding an item:** give it the next `TD-N`, fill every column, and say *why it is acceptable for
  now*. **An item with no "why" is drift, not debt** — drift gets fixed, debt gets scheduled, and
  conflating the two is how a register becomes a graveyard.
- **A debt is not a defect.** A defect is something that behaves wrongly; a debt is something that
  behaves acceptably but constrains the future. If a row describes something actively broken, it does
  not belong here — it belongs in [NEXT.md](NEXT.md) as work.

## Active & latent debt

Every item below was created by the **2026-08-08 bootstrap pass** ([HISTORY.md](HISTORY.md)). That is
unusual and worth stating: this is not accumulated cruft, it is the honest cost of authoring a
structure before there was a toolchain to verify it against. The register starts full on purpose,
because the alternative — a pristine-looking register beside an unverified repository — is exactly
the false-confidence failure the [evidence standard](OPERATING_MODEL.md#7-the-evidence-standard--what-it-works-is-allowed-to-mean)
exists to prevent.

Treating its absence as a reason to skip compiling was the defect, not the absence itself. | **TD-3** | tooling (boundary check) | 🟡 latent | **The modularity boundary check reads source text, not a compiled assembly graph.** `tools/doc-audit/audit.py` enforces the Core/Shell split and the module isolation rules by inspecting `using` directives, `[DllImport]` attributes, namespace references and `ProjectReference` elements in `.cs`/`.csproj` files. That is a real, working check — it catches the ordinary way the rule gets broken, which is someone adding an import — but it is **defeated by reflection, by a fully-qualified type name written inline, by a source generator, or by a transitively-referenced package that drags Windows types in**. A green boundary result is evidence, not proof. Accepted for now because the alternative (Roslyn analysis, or inspecting compiled assemblies) requires the toolchain that **TD-1** says does not exist, and because the text check is strictly better than nothing today. | Replace or supplement with a Roslyn-based analyzer, or an assembly-reference check run after `coord build`, so the rule is enforced against what actually compiles. Keep the text check as the fast pre-build pass. **When it is replaced, prove the new check fails without the fix** — deliberately violate the boundary and watch it go red, per the operational rule in [OPERATING_MODEL §7](OPERATING_MODEL.md#7-the-evidence-standard--what-it-works-is-allowed-to-mean). | The first time a **Core** project legitimately needs a Windows type (forcing a considered exception rather than a blanket rule), **or** the first time someone works around the check with reflection or a fully-qualified name — whichever happens first. |
| **TD-4** | CI | 🟡 latent | **The Linux CI runner cannot build or test the Windows-targeted projects.** ⚠ **Narrowed 2026-08-08:** a `windows-latest` job now compiles them, so the gap is no longer "invisible to CI entirely" — it is that they are *compiled but never executed or exercised*, which is a much smaller and much better-defined gap. On the Linux runner only the `net9.0` **Core** projects are buildable and testable; everything targeting `net9.0-windows10.0.19041.0` — both pillar Shell adapters, the WinUI host, and every P/Invoke path — is compiled on the Windows runner and never run. So the automated gate proves the risky half *compiles* and proves nothing about its behaviour. Accepted because Core is where the decision logic deliberately lives (ADR 0003) and because a Windows runner is a real cost for a personal project with one developer. The danger is not the gap itself — it is forgetting the gap exists and reading a green CI badge as coverage. | Add a Windows job to `.github/workflows/ci.yml` that at minimum **compiles** the Windows-targeted projects (compilation alone would catch most of what escapes today); full behavior still needs [runbooks/manual-validation.md](runbooks/manual-validation.md), which no runner can perform. | The first Shell-adapter regression that reaches a real desktop and that a Windows *compile* job would plausibly have caught. Price the runner against that specific pain, not in the abstract. |
| **TD-5** | module contract | 🟡 latent | **No module exists, so [MODULE_SPEC.md](MODULE_SPEC.md) has never been validated by a real implementation.** The membrane, the lifecycle interface, the capability and trigger-intent declarations, the settings shape and the shelving contract are all specified in detail and consumed by nothing. A specification with zero implementations is a hypothesis written in the imperative mood — it will read as authoritative to the next session precisely because it is thorough. Historically the first real consumer always changes the contract; the risk is that the spec's confidence discourages changing it. | Build **Zones** (P3) against the spec as written, note every place it fought back, and revise the spec against reality in the same session — not later. A second, unrelated consumer (**Chrono**, P4) is what actually tests the contract, since the first one is always co-designed with it. | P3 begins. Until then, treat every MODULE_SPEC claim as designed-but-unproven. |
| **TD-6** | platform (update / delivery channel) | 🟡 latent | **The update/delivery channel is designed but unbuilt**, while [OPERATING_MODEL §3](OPERATING_MODEL.md#3-capture-is-free-building-costs) names it explicitly as one of the four retrofit-expensive seams — the pipe every deferred feature must later travel through. The seam is planned for P1 and the working path for P5, so today there is a documented intention and no mechanism. The specific exposure: the moment the app is installed anywhere the developer is not sitting, *"we can add that later"* stops being true for that install, and the only remedy is a manual re-copy. | P1 builds the seam (packaging identity, version comparison, an install-over path that preserves settings); P5 makes it work end to end and records the real procedure in [runbooks/release-and-update.md](runbooks/release-and-update.md), including a settings migration proven by a test that **fails without the migration**. | The first install on a **second machine** — at that moment this row goes 🔴 and P5 is promoted to the Active focus regardless of what else is in flight. |
| **TD-7** | tooling (`coord`) | 🟡 latent | **Only the pure-Python subcommands of `coord` have ever been executed.** `coord audit`, `coord map` and `coord doctor` were run during the bootstrap and their results are real. `coord test`, `coord build` and `coord run` — the subcommands that shell out to `dotnet` — have **never executed their `dotnet` path even once**, because no SDK was present. Their argument construction, working-directory handling, exit-code propagation and error reporting are all unverified code in the one tool every future session will use first. A wrapper that mis-reports a failed build as success would be failure shape 1 (a check that cannot fail) sitting at the entry point of the whole workflow. | Exercise each `dotnet`-invoking subcommand on the Windows machine during the **TD-1** pass, and specifically confirm that a **deliberately broken build** makes `coord build` exit non-zero and say so plainly. Verify the failure path before trusting the success path. | Step 1 of the **TD-1** pay-down — the same session, not a follow-up. |
| **TD-8** | tooling (doc-audit) | 🟡 latent — **partly paid 2026-08-08** | **The mechanical checker has no self-test suite, so its checks are not *repeatably* proven capable of failing.** `tools/doc-audit/audit.py` implements fifteen checks. At bootstrap closeout, adversarial verification planted violations and confirmed that `frontmatter`, `doc-link`, `related`, `code-ref`, `adr-gap`, `adr-format`, `map-sync`, `shelving` (both variants) and all four `boundary` vectors genuinely fire — so the boundary check in particular is demonstrably not a stub. **Two guards were also found to be incapable of failing and were fixed, each with a recorded A/B proof:** `updated-flag` compared `updated` for *equality*, so a doc edited **and back-dated** in the same commit passed silently (now compares `<=`, i.e. "did not move forward"); and `genmap.py` treated every unrecognised argument — including `--help` — as "rewrite the map", so a mistyped gate invocation silently repaired the drift it was asked to detect (now validates argv). **What remains** is that all of this was one-shot manual proof: nothing re-runs it, so a future edit can re-open any of these holes and nothing will notice. A check whose pattern silently matches nothing reports success forever and is indistinguishable from a comment. | Add a small fixture-based test suite: for each check, one input that must produce the finding and one that must not. Stdlib `unittest` is enough; no dependency, no toolchain, runnable today. Until then, when adding or modifying a check, **break something on purpose and watch it go red** before trusting it. | The first time a check is added or modified, **or** the first audit where a finding that should obviously have fired did not. |
| **TD-9** | validation apparatus | 🟡 latent | **[runbooks/manual-validation.md](runbooks/manual-validation.md) has never been executed by anyone.** It is the *only* evidence class that can close the P2, P3 and P4 gates — everything a user can see is validated there and nowhere else — and it is currently an untested procedure written by someone who has never performed it. Its steps may be ambiguous, out of order, or impossible on a real desktop; a checklist that cannot be followed produces an unreproducible pass, which is worse than no checklist because it is recorded as evidence. | Execute it start to finish the first time there is anything at all to validate (even the P1 reference module in the tray), and **revise it as you go** to say what actually had to be done. A runbook is a record of a procedure that worked, not a plan for one. | P1 produces the first visible artifact — the reference module appearing in the Shell. |
| **TD-10** | Shell / UI stack | 🟡 latent | **The UI stack is chosen on reputation, not experiment.** WinUI 3 on the Windows App SDK is decided (ADR 0002) for stock-Windows fidelity, but nothing has been built with it here: tray-icon behavior, unpackaged versus packaged deployment, the runtime bootstrapper dependency, per-monitor DPI awareness in the settings window, and startup cost for a process that must sit resident all day are **all unmeasured**. These are the areas where this particular stack is known to be fiddly, and they sit exactly where a resident tray utility lives or dies. Accepted because the decision has to be made before any UI can be written and the alternatives carry their own unmeasured risks. | Build the smallest possible spike during P1 — a tray icon plus one settings window, unpackaged — and record what deployment actually required. If tray or unpackaged deployment proves genuinely hostile, that is an ADR revisiting ADR 0002, not a workaround buried in the Shell. | P1 Shell bring-up. |
| **TD-11** | performance | 🟡 latent | **No performance baseline exists for a process designed to sit resident all day.** There is no measurement of idle memory, idle CPU, startup time, or input-hook callback latency — and the last of these is on the desktop's critical path, where a slow callback stalls the whole machine rather than just this app. Without a baseline, any future claim that the toolbox is "lightweight" is unfalsifiable, and any future regression is invisible: you cannot notice a doubling of something you never measured. | Take the first measurements as soon as the host runs with the reference module loaded — idle working set, idle CPU over a few minutes, cold start, and once Conduit exists, hook-callback duration. Write the numbers into a runbook with the machine they came from. Measure before optimizing anything. | P1 produces a runnable host, **or** the process becomes measurably annoying in daily use — whichever comes first. |
| **TD-12** | docs (ADR references) | ⚪ cosmetic | **Many cross-document ADR references are plain text (`ADR 0007`) rather than Markdown links to the file**, a convention adopted during the bootstrap because the ADR filenames were being authored in parallel and a guessed slug would have produced a broken link — which the `doc-link` check treats as an ERROR. The consequence is that the checker cannot verify these references at all: an ADR that is renumbered, retitled or superseded leaves stale plain-text mentions scattered through the docs with nothing to catch them. Genuinely cosmetic today (ten ADRs, all fresh) and genuinely corrosive at fifty. | Convert plain-text ADR references to real Markdown links now that the filenames are fixed, so `doc-link` covers them; or add an `adr-ref` check that resolves `ADR NNNN` text against the decisions directory by number, which is more robust to renaming than a path link. | The first ADR that is superseded or renumbered, **or** whenever the ADR count passes roughly twenty and manual tracking stops being credible. |
